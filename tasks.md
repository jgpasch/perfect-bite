## Redesign: direction B, "Pantry"

Goal: restyle the app to direction B ("Pantry") from the redesign canvas (https://claude.ai/artifact/LPFfBGAmXX8mDtZHME9nQ3). Friendly and tactile: lists are tiles, each aisle has its own colour so you can find your place in a long list at a glance, round checks, soft white cards on a pale green ground. The boards are saved as HTML in `docs/design/pantry/` (`lists.html`: screens 01–04, `recipes.html`: 05–08, `settings.html`: 09–12); read the screen you're building in full before starting, and treat the 390×844 phone frames as the reference. These tasks change the look only: same screens, same data, same behaviour. Don't add features the boards show but the app doesn't have yet (e.g. "+ New aisle" and "+ New" aisle chips, list tile icons): leave them out and list them in progress.md. The native tab bar (`NativeTabs`) and native headers stay native; the boards' floating tab bar is only a mock, so just set its tint. Every colour and size comes from `useTheme()`; no hex values or font sizes in components. Keep Dynamic Type working, touch targets ≥ 44 pt, and text contrast ≥ 4.5:1 in both schemes.


## Item details: tap to open

Goal: tapping an item's name opens its details, and only the round check checks it off. Today the whole row toggles the check (`src/features/lists/item-row.tsx`) and the edit sheet (`src/app/list/[id]/item/[itemId].tsx`) opens only on a long-press nobody finds. These tasks change behaviour, so update `docs/spec.md` (4.2, 4.3.2, and anywhere else that says long-press or row-tap) in the same task as the code, and keep the Pantry look from DESIGN.md.

- [ ] Tap the name to open, tap the check to check. In `ItemRow`, make `CheckCircle` its own pressable that calls `onToggle` (hit area ≥ 44 pt, grown with `hitSlop` rather than a bigger circle), and make the rest of the row (name, second line, amount) a separate pressable that calls `onEdit`. Drop the long-press, since a tap now does it. In selection mode (Make recipe / Add to recipe) a tap anywhere on the row still selects, as today. Swipe-to-delete stays. Do the same in By recipe view and anywhere else `ItemRow` is used. Accessibility: the check is a `checkbox` labelled "Check off <name>" with its checked state; the row body is a `button` with the current row label and the hint "Opens details"; keep the Edit / Delete custom actions on the row, and add a "Check off" / "Uncheck" one so VoiceOver users can do it without finding the circle. Check the pressed-state opacity only dims the part that was pressed. Add a test for any pure helper that changes (e.g. the labels). Manual check in the simulator: tapping a name never checks it, tapping the circle never opens the sheet, scrolling with a finger on a row does neither.
- [ ] Amount and unit in the details sheet. Make quantity and unit quick to change without typing: a number field and a unit button side by side on the Amount row, with the − / + stepper beside them (same step sizes, rounding and "saves right away" behaviour as spec 4.4). Replace the `ActionSheetIOS` unit list with a native menu (check the SDK 57 docs for the current menu component, e.g. `@expo/ui` or the Stack toolbar menu; don't add a third-party library) grouped as Count / Weight (g, kg, oz, lb) / Volume (ml, l, tsp, tbsp, cup, fl oz, pt, qt, gal) / Packages (can, jar, bag, box, bunch, clove, pinch, dozen), with the current unit ticked and the ingredient's usual unit (4.2) listed first and marked "Usual". Picking a unit still keeps the number. Typing a number saves on blur or Save; an empty field clears the amount; a total that isn't a single amount (`2 cans + 400 g`) stays editable as text with the stepper and unit button disabled, as today. Put the grouping in a pure helper next to `amount-stepper.ts` and test that every supported unit (spec 4.2) is in exactly one group.
- [ ] More in the details sheet. Add: (1) a "Got it" / "Still need it" toggle near the top that checks or unchecks the item (same write as the row's check, so undo and sync behave the same) and closes the sheet when it checks; (2) in the "Added" card, rows that came from a recipe show the recipe name and open that recipe when tapped; (3) "Move to another list…", which lets you pick another list in the same household and moves the item with its contributions, combining with an existing item there exactly as a single add would (4.4: Combine, toast with Undo on the destination list's screen) — put the move in the lists data layer with a test for the combine case, and leave it out when the household has only one list; (4) "Checked <relative time> by <name>" under the title for a checked item, if who checked it is already stored (otherwise leave it out and note it in progress.md). Update the spec's edit-sheet description to match.

## New items stay in the order you added them

Goal: while you're writing a list, items stay in the order you typed them, so nothing jumps into an aisle further down. When you go shopping, you switch to By aisle. This is display only: no schema change, no migration, and categorization keeps running on add exactly as today, in the background, so By aisle is already sorted when you switch to it. Update `docs/spec.md` 4.2 and 4.6 in the same task as the code, and keep the Pantry look from DESIGN.md.

- [ ] "Added" view mode. Add a third segment to the list screen's `SegmentedControl` (`src/app/list/[id]/index.tsx`), ordered **Added** | **By aisle** | **By recipe**. Added is the default for a list with no saved choice; the choice stays remembered per list on the device as today (`viewModeKey`). Existing saved choices are kept, so no one's list changes under them. In Added view, show unchecked items in one `Card` (no section header, or a plain "N to get" one if the board style needs a header), ordered by when they went on the list: the earliest `createdAt` among the item's current contributions, oldest first, newest at the bottom next to the add bar. That ordering means a Combine onto an existing item keeps its place (it highlights there as today), and re-adding a checked item, whose contributions 4.4 replaces, moves it to the bottom like a new add. Ties go by item id. Each row shows its aisle as the small aisle dot (`aisleColor`) beside the name, or the dashed amber check and "Sorting…" label while its category is pending, so you can still see where things will go. Check, tap-to-open, swipe-to-delete, the add highlight (aisle soft tint, or `pendingSoft` while sorting) and the undo toast work as in By aisle. Adding an item keeps the new row visible: if it's off-screen, scroll so it's just above the add bar. Checked items keep the collapsed Checked card at the bottom. Select mode (Make recipe / Add to recipe) works from Added too: entering it switches to By recipe as today. Switching to By aisle uses a short layout animation if FlatList allows it cheaply (respect Reduce Motion); otherwise no animation. Put the ordering in a pure helper in `src/features/lists/list-view.ts` (e.g. `orderByAdded(items)`) and test it: oldest-first by earliest current contribution; Combine doesn't move an item; a checked re-add moves to the end; an item with no contributions (if any can exist) falls back to the item's own `createdAt`; ties by id; checked items excluded. If `ItemView` doesn't carry the timestamps needed, add them in `groupItems` and extend its test. Accessibility: the segment is a `tab` labelled "Added", with the hint "Items in the order you added them". Spec: in 4.6 make it three modes and describe Added and its ordering; in 4.2 say where a new item appears in each mode. Manual check in the simulator, noted in progress.md: in Added, type five items quickly, including a new name such as `yuzu kosho`. They stay in typed order, and the new one shows Sorting… and then its aisle dot without moving. Switch to By aisle and each item is in its aisle.
