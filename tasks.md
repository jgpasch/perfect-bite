## Stock photo search

Goal: in the Choose a photo sheet (spec 4.5), a recipe's photo can also come from a search of free stock photos (Pexels), alongside From the page, Photo library and Take photo, which stay as they are. The sheet opens from both the Add photo tile and Change photo…, so search shows in both. A picked stock photo is downloaded, shrunk and uploaded like a library photo, so it's the household's own photo (`photo_path`) and keeps every own-photo behaviour (disk cache, offline, cleanup); it also carries a credit to the photographer and Pexels, as Pexels' API guidelines ask. Read https://www.pexels.com/api/documentation/ before the Edge Function task. The Pexels key (`PEXELS_API_KEY`) is added by hand after this section; until then the function answers `503 unavailable` and the section shows its failure state, and every test uses a fake Pexels.

- [x] The `photo-search` Edge Function (spec 6.11, new). Modelled on `recipe-photos` (`supabase/functions/recipe-photos/`: `index.ts`, `handler.ts`, `request.ts`, `store.ts`, Deno tests). JWT-authenticated `POST` of `PhotoSearchRequest` (`src/shared/schemas/photo-search.ts`, shared with the app): `{ query: string (trimmed, 1–100 chars), page: int 1–10 (default 1) }`. Answers `200 { photos: PhotoSearchResult[], hasMore: boolean }`, each `{ id, thumb, full, width, height, author, authorUrl, pageUrl, alt }` from Pexels' `GET /v1/search` (`per_page` 20, `orientation=landscape`; `thumb` = `src.medium`, `full` = `src.large2x`, `pageUrl` = `url`, `author`/`authorUrl` = `photographer`/`photographer_url`; drop any photo whose URLs aren't `https://`). The key is `PEXELS_API_KEY`, sent only from the server; unset, the function answers `503 unavailable` before anything is counted. Errors: `invalid_request` (400: not JSON, or a bad query or page, before anything is counted), `413` over 8 KB, `rate_limited` (429), `unavailable` (503 with `Retry-After: 3600`: the global cap, no key, or Pexels answering 429), `search_failed` (502: Pexels failed or timed out after 8 s). Limits (one migration, as `check_recipe_photos_limit`, service role only, a refused request uses no budget, usage rows pruned daily): per user 20 a minute and 100 a day, and globally `PHOTO_SEARCH_DAILY_CAP` (default 3,000) a day. A cache, `private.photo_search_cache` (key = the query lowercased with whitespace collapsed, plus the page; the answer as jsonb; fetched_at), answers a repeat search for 24 hours without calling Pexels (a cache hit still counts against the user's limit but not the global cap); pruned daily. Add `PEXELS_API_KEY=` and `PHOTO_SEARCH_DAILY_CAP=` to `supabase/functions/.env.example` (or wherever the other function env vars are documented) and register the function in `supabase/config.toml` if the others are. Deno tests with a fake Pexels: the mapping, non-https photos dropped, `hasMore`, a cache hit doesn't call Pexels, each error, no key. pgTAP for the limit function and cache pruning. Write spec 6.11 in the style of 6.9 (flow, errors, cost) and add the function to 8.3's list if there is one.
