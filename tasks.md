## Combine across languages is a household setting

Goal: a household chooses whether the same thing typed in English and Spanish is one item. The links stay in the catalog whatever the setting; the setting only decides whether this household's lists use them. Aisles stay shared either way.

- [x] Household setting for Combine across languages (spec 4.15, 4.4, 4.2, 5). A migration adds `households.combine_languages boolean not null default false`; it syncs like the household's other fields (SQLite schema, pull, `mutate.ts`), and any member can change it (check how the household name is changed today and follow that path, server checks included). Settings shows one row per household, **Combine English and Spanish names**, a switch, with the footnote "Leche and milk become one item on your lists." (en and es strings). When it's off, the "already on list" tint and every Combine path compare the item's own key only, as before links existed: `alreadyOnListMatch`, `detectDuplicate` and `planBulkAdd` callers in `items.ts` (`addItem`, `addSiriItem`, `addItemsBulk`, `restoreItem`), `pull.ts`'s `closeClashingItems`, and the family merge in `private.apply_mutation` (a new migration redefining it from `20261020120000_family_combine.sql`; it reads the list's household's setting). When it's on, they behave as today. Aisle overrides keep using the family key whatever the setting (moving `milk` still moves `leche`). Turning it on merges nothing already on a list: twins combine the next time one of them is added or reopened. Turning it off leaves combined items as they are. Tests: in the app, each path with the setting off (two items, no tint) and on (as today), both directions; a household with it on and another with it off in one account; turning it on with open twins on a list leaves both until the next add; pull with it off keeps a local twin; pgTAP for `apply_mutation` off and on and for who can change the setting; the existing family tests turn the setting on. ## Favorite and Want to try

Goal: a household can mark recipes **Favorite** and **Want to try**, and filter the Recipes tab by them. They're tags a person picks, never the AI. Both tasks touch the same files (`recipe-tags.ts`, the Tags and Filters sheets), so they run in order, in this one section.

- [ ] A "Saved" tag facet: Favorite and Want to try (spec 4.14, 5). A migration widens the `recipes_tags_shape` check (`20261013180000_recipe_tags.sql`) to allow the `saved` key; `RecipeTagsSchema` and `emptyRecipeTags` gain it (a stored value without it reads as `[]`, so existing recipes and older rows are fine). The AI never sets or clears it: `import-recipe`/`extract-recipe` and `suggest-tags` neither ask for nor return `saved`, the model's answer schema leaves it out, and a suggestion in the Tags sheet replaces the other five facets' picks but keeps `saved` as picked. A recipe with only `saved` tags isn't "untagged" for the Filters sheet's Untagged count, and "Tagged when you imported it" ignores it. Everything else is the existing facet behavior: toggle pills in the Tags sheet, pills on the recipe screen, a group in the Filters sheet (shown only when some recipe has a value, OR within the facet), and active chips ("Favorite ✕").
