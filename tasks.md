## Ingredient history for autocomplete (spec 4.2)

Goal: typing `chi` suggests what this household actually buys (chicken thighs, chicken breasts) ahead of catalog items they never use (chicken salad). History is per household, as spec 4.2 says ("the household's recently used ingredients").

- [ ] Add a local `ingredient_usage` table in `src/db/schema.ts` with columns `household_id`, `ingredient_name` (normalized key), `display_name` (the most recent text the household typed for it), `use_count` (integer, default 0), `last_used_at` (timestamp_ms), `hidden_at` (nullable timestamp_ms), plus the shared `timestamps`; primary key `(household_id, ingredient_name)`. Generate the Drizzle migration as `0004_ingredient_usage.sql` and update `migrations.js`. Test that a row can be inserted and read back and that the primary key rejects a duplicate pair.
- [ ] Add `src/features/lists/usage.ts` with `recordUsage(tx, householdId, ingredientName, displayName, at)` (upsert: `use_count + 1`, `last_used_at = at`, `display_name` = the new text, clear `hidden_at`) and `unrecordUsage(tx, householdId, ingredientName)` (`use_count - 1`, never below 0; delete the row at 0). Pure DB helpers, no callers yet. Test: first use creates count 1; second use increments and updates display name and time; unrecord decrements; unrecord at 1 deletes the row; unrecord on a missing row is a no-op; a hidden row is unhidden by a new use.
- [ ] Call `recordUsage` inside the same transaction from every path that adds an ingredient to a list: `addItem` and `addItemsBulk` in `src/features/lists/items.ts` and `addRecipeToList` in `src/features/recipes/add-to-list.ts`. Count once per ingredient per add, including when the add combines into an existing item. `undoAdd` must call `unrecordUsage` so an undone add (a typo, say) doesn't count. Test each path, including combine and undo.
- [ ] Count recipe ingredients too: when a recipe ingredient is created (recipe CRUD and `addItemsToRecipe` in `src/features/recipes/from-list.ts`), call `recordUsage`. Don't double count when the recipe is later added to a list. Simplest rule: recipe creation records usage, and `addRecipeToList` records it as usual, since putting it on a list is a real use. Write the rule you pick as a comment in `usage.ts`. Test that a recipe-only ingredient shows up in usage.
- [ ] Backfill history for existing data: a one-time step (run from `loadCatalogSeed` or app start, guarded by a device setting like the seed fingerprint) that builds `ingredient_usage` from existing non-deleted `list_item_contributions` (joined to `list_items`) and `recipe_ingredients`, with `use_count` = number of contributions and recipe rows and `last_used_at` = the latest `created_at`. It must be idempotent and must not overwrite rows that already exist. Test with seeded lists and recipes, then run it twice.
- [ ] Add a pure ranking function in `src/domain/suggestion-rank.ts`: `rankHistory(rows, query, now)` filters rows whose display name or key starts with the query or has a word that does, then sorts by a frecency score `use_count * 0.5^(days since last_used_at / 30)`. Whole-name prefix matches outrank word matches at equal score; the final tiebreak is shorter name, then alphabetical. Hidden rows are excluded. Test with concrete values: a frequent old item vs. a once-used recent one, a word match (`thighs` matches `chicken thighs`), a prefix match beating a word match, hidden rows dropped, and an empty query returning [].
- [ ] Rewrite `searchRecentItems` in `src/features/lists/items.ts` (or move it to `usage.ts`) to read `ingredient_usage` for the household and order with `rankHistory`, instead of grouping `list_items` by recency. Pre-filter in SQL with the existing `like` patterns and let `rankHistory` do the ordering. Update the existing tests in `src/features/lists/__tests__/items.test.ts`. Test that a deleted list item no longer drops out of history (history outlives the item) and that an item used 5 times outranks one used once yesterday.
- [ ] Change `getSuggestions` in `src/features/lists/suggestions.ts` so household history wins: if history returns 2 or more matches, show only history (up to `limit`); with fewer, fill the remaining slots from `searchCatalog`, deduped by key as now. As the user keeps typing, history drops out naturally (`chickp` no longer matches chicken), so catalog items like chickpeas still appear. Test: with chicken thighs and chicken breasts in history, `chi` returns exactly those two, without chicken salad; with one history match, catalog fills the rest after it; with no history, catalog-only results are unchanged; `2 lbs chi` behaves the same as `chi`.
- [ ] "Remove from suggestions": long-pressing a history suggestion in the add bar's autocomplete offers "Remove from suggestions", which sets `hidden_at` via a new `hideFromSuggestions(householdId, ingredientName)` in `usage.ts`. Using the ingredient again unhides it (already handled by `recordUsage`). Catalog-only suggestions don't get this action. Follow DESIGN.md for the menu. Test the data function: hidden rows are excluded from `getSuggestions` and come back after a new use.
