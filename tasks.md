## Architecture: sync

- [x] Pull never loses rows that share a timestamp (architecture review, sync bug). `fetchRows({ at })` (`src/sync/pull.ts:428`) fetches every row changed at exactly one `updated_at` with no paging, so PostgREST caps it at `max_rows = 1000` (`supabase/config.toml:18`) and `pullTable` then moves the cursor past the rest. One transaction stamps all its rows with the same `now()`, and the catalog seed migrations do that to ~3500 `ingredients` rows, so `catalog:ingredients` drops about 2500 of them. Switch the pull to a compound cursor `(updated_at, id)` ordered by both (`.or('updated_at.gt.x,and(updated_at.eq.x,id.gt.y)')`, with a composite key encoding for tables keyed on several columns), migrating the stored cursors, and treat a page of exactly `max_rows` as "more". Unit tests: 2500 rows with one `updated_at` all arrive across pages, and an existing device's stored cursor keeps working.
- [x] Sign-out waits for sync (architecture review, sync race). `signOutAndWipe` (`src/features/auth/sign-out.ts:29-33`) and `deleteAccount` (`src/features/auth/delete-account.ts:111-132`) call `wipeLocalData()` while a push or pull may be in flight (`pushBriefly` only races a 3 s timer; `pullNow` isn't awaited), so a `commit()` (`src/sync/pull.ts:456-480`) can write the old user's households and cursors into the wiped database, and the next account then sees them (`listsWithCountsQuery` has no membership filter). - [x] Pull keeps local edits pushed during its fetch (architecture review, sync race). `commit()` builds `pendingIndex` at apply time (`src/sync/pull.ts:225-228,283,299,308,457`) but its rows were fetched earlier, so a push `settle()` (`src/sync/push.ts:144-151`) between fetch and commit lets a stale server row overwrite clock-less fields (`user_settings.default_list_id`, `user_household_category_order.category_ids`, `households`) and lose counter deltas.
