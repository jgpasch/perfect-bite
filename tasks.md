## Admin and plans

Goal: run the app from the Supabase dashboard (Authentication → Users, Table Editor, SQL Editor, logs), with no custom admin portal, and give each user a plan that decides which AI features they get. The dashboard runs as `postgres` and doesn't know the app's rules, so a change that has rules (deleting a user) goes through a tested SQL function in a new `admin` schema, run as a SQL snippet instead of editing rows by hand. A change that has no rules beyond the table's constraints (a user's plan: one `user_plans` row) is made in the Table Editor. `admin` is not in the API's exposed schemas (`supabase/config.toml`), and its functions have execute revoked from `public`, `anon`, `authenticated` and `service_role`, so only the dashboard can call them. Each admin function writes one `admin_actions` audit row in the same transaction.

**Plans.** A feature is a text key; a plan is a named set of features. v1 features: `categorize` (the LLM categorizes new ingredient names, 6.1), `recipe_import` (importing a recipe from a link, share sheet or in-app, 4.10; it categorizes in the same request, so it's only ever in a plan with `categorize`) and `recipe_import_photo` (for the future photo import; nothing checks it yet). Plans: **base** (no features: no AI at all), **standard** (`categorize`; the default for anyone without an assignment) and **plus** (`categorize`, `recipe_import`, `recipe_import_photo`). Plans are **per user**: members of one household can be on different plans. Build it so plans can become per household later (so one paying member can't share their plan by inviting anyone) by changing only the server's resolution: every check goes through `has_feature(user, feature, household)` and the app asks `my_features(household)`, both given the household the action is in when it's known; today the household argument is ignored. Edge Functions enforce entitlements; the app only hides or skips what isn't enabled.

**A base user and new ingredients.** Known ingredients (the seed, and anything already categorized by anyone) work as today: their aisle and default unit come from the catalog, offline too. A name that's new to the app goes into **Other** at once (never "Sorting..."), with the default unit `count`, and isn't sent to the LLM: the base user's app never calls `categorize-ingredients` (adds, catch-up, recipe adds), and the server answers `not_entitled` if it's called anyway. The server's ingredient row stays `pending`. The household can still move it to another aisle (a household override, 4.3.2) and its unit changes go into the household's unit history (`ingredient_unit_usage`) as usual. The first time a user with `categorize` adds that name, or their device's catch-up meets it (including on a list item synced from a base household-mate), it goes to the LLM; the result lands in the global catalog, so everyone, base users included, gets the real aisle and default unit from then on. A user moved from base to standard has their own leftover names categorized by their next catch-up.

Defining new plans from SQL by hand is fine for now; there's no `create_plan`. The admin portal stays in `tasks-future.md`. Spec: add a new section 4.12 "Admin and plans" and update 4.3.1, 4.7, 5, 6.1 and 6.3 as each task changes them. Don't push to or deploy hosted Supabase; that's done by hand.
