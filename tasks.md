## Plans per household

Goal: a plan belongs to a household, not a user, and covers only the two AI features that cost real money: **recipe import** (link and photo, one allowance; the tags and step match an import makes are part of it) and **AI photos**. Everyone in a household gets its plan and shares its monthly allowance, so inviting people doesn't multiply it. Everything else the AI does is for everyone on every plan with no monthly limit: **categorize** (it fills the global catalog, so it helps everyone, and nobody gains from overusing it), **step matching** for recipes typed or edited by hand, and **Suggest tags**. Those keep per-user per-minute limits and gain per-user daily ceilings, which stop a scripted account rather than a person. Every number (the plans' monthly limits and the per-minute and daily ceilings) is a table row an admin edits in the portal, never a constant in code.

Decisions behind it, for the spec task to write down:
- **Feature keys** become two: `recipe_import` (link import and photo import alike; `recipe_import_photo` folds into it) and `recipe_photo_ai`. `categorize`, `step_ingredients` and `recipe_tags` stop being plan features. The import rule (an import needs `categorize`, `plan_features_import_needs_categorize`) goes away with them.
- **Plans**, renamed so the names say what they are: **founding** ("Founding", replacing plus: `recipe_import` 50 a month, `recipe_photo_ai` 20 a month; the default until paid plans launch), **unlimited** (both, no monthly limit), **free** ("Free", replacing none: neither, though categorize, step matching and Suggest tags still work). **basic** is deleted (it had only categorize and step matching, which everyone now has); a household on it moves to free. The ids change too (they're referenced by `household_plans` and the audit log, so this is the last cheap moment): plus becomes `founding` and none becomes `free`; old audit rows keep the old ids as written. A household's first 30 days (`households.created_at`) get twice its plan's monthly limits, as now.
- **Every household has an explicit plan.** A household's plan is its `household_plans` row and nothing else; there's no "unassigned, so the default". Creating a household (`create_household`, `private.create_personal_household`) writes its row with the plan that is the default at that moment, and the migration gives every existing household one. "Default" only means the plan new households start on: changing it never moves an existing household. A household with no row (which shouldn't exist) has no features. In the portal a household's plan can be changed to another plan but not cleared.
- **Founding households** (every household made before paid plans launch) stay on founding, free of charge, for good, through their explicit rows. Until paid plans launch, new features may be added to founding; after that, founding is frozen: a new feature goes into a new plan, never into founding, so founders get only what founding had at launch. Changing founding's limits is allowed and applies to founders. `docs/admin.md` gets a "Launching paid plans" section: create the paid plan (its own name) and make it the default (new households only); existing households keep founding; never add a feature to founding.
- **One household per new user.** `create_household` refuses (`already in a household`, `P0001`) when the caller is already a member of any household, so a user can't make extra households to multiply allowances. The app only ever creates one when the user has none (`ensureStarterData` at sign-up, Start my own list), and the server makes one when a user leaves their only household. Leaving your only household (deleting it, as its last member) and getting a fresh one with a fresh allowance and first month is allowed: it costs every list and recipe, so it isn't worth farming.
- **Safety limits**, per user, the same on every plan, in a table (below). Seeded: categorize 60 requests a minute and 500 LLM-bound names a day; step matching 30 a minute and 100 a day; Suggest tags 20 a minute and 50 a day; link import 10 a minute; photo import 5 a minute; recipe imports (link and photo together) 100 a day; AI photos 40 a day. ## A user's activity log in the portal

Goal: an admin opening a user in the portal sees everything that user did, newest first, and can filter it: every change of theirs that reached the server (lists and items, recipes, the meal plan, aisles, staples, settings, household and invite actions, devices), their AI requests, and what admins did to their account. Only server writes: nothing the app does without writing (opening a screen, searching, viewing a recipe) is logged, and an offline edit shows when it syncs. Each entry is a named action ("item.checked", "plan.added") with the data that action needs to be read and filtered: ids, the names of what it touched as they were then, and small values (a day and meal, a quantity and unit, a role, on/off), never free text the user wrote (notes, recipe text, steps). Kept 90 days; deleting the account deletes its entries. The spec isn't updated yet: the first task does it. Today nothing records who changed a row after it was made (only `recipes.added_by`, `list_item_contributions.added_by`, `meal_plan_entries.added_by`, `ai_calls.user_id` and `admin.admin_actions` say who), so this is new.

Why triggers: every write reaches a table, whichever path it took (`apply_mutations`, the household functions, direct writes to `user_settings` and `user_category_order`, the push token functions), so a trigger can't be missed by a path added later. Logging inside `apply_mutations` would miss the other paths and see no more than the trigger does (a table, a row, its fields). The trigger only sees rows, not what the user meant, so it translates each row change into a named action, below; one gesture that writes many rows (a recipe with 20 ingredients) logs many rows that share a `txid`, and the portal folds them.
