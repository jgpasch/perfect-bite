## Two-device sync tests

Goal: end-to-end tests that prove a change on one phone shows on another phone with the same list open, without leaving the screen or pulling to refresh. Two simulators run at once against local Supabase and the same Metro. A Maestro flow drives only one device, so `scripts/e2e.sh` runs short flows in turn, alternating devices (`maestro --device <udid> test <flow>`). A flow that doesn't call `launchApp` leaves the app as it is, so each phone keeps its list open, with its Realtime channels connected, while the other one acts. Today a change takes about 1.5–2 s to arrive: a 1 s push debounce (`PUSH_DEBOUNCE_MS`, `src/sync/push.ts`), then the 300 ms Realtime batch (`REALTIME_BATCH_MS`, `src/sync/realtime.ts`), then a household pull. So the tests wait up to 5 s: they check that the change arrives live, not how fast. Reuse the existing pieces in `.maestro/` (`subflows/sign-in.yaml`, `scripts/new-email.js`, `scripts/sign-in-code.js`); no new dependencies.

- [ ] Script: run on two simulators. `scripts/e2e.sh` keeps running the top-level `.maestro/*.yaml` tests on the booted device as today, and adds a two-device phase: it finds or creates a second simulator named "Perfect Bite e2e B" (`xcrun simctl create`, same device type and runtime as the booted one), boots it, and installs the same debug `.app` the first device runs (found from `xcrun simctl get_app_container <udid A> com.jgp.perfectbite`), so `yarn expo run:ios` once is still the only build step. Both connect to the same Metro on 8081. The phase runs each test in `.maestro/two-devices/`, where a test is a folder of numbered steps (`01-a-*.yaml`, `02-b-*.yaml`, …): the `a`/`b` in the name says which device, and the script runs them in order with `--device`, stopping at the first failure and saying which step and device failed. Values shared between steps (the two emails) are passed as `-e NAME=value`, generated by the script, since Maestro's `output` doesn't outlive one run. The second simulator is left booted at the end (booting is slow), with a line saying how to shut it down. `yarn e2e --only-two-devices` and `--skip-two-devices` select a phase. Update the comments at the top of `scripts/e2e.sh` and `.maestro/config.yaml` (it should not pick up `two-devices/` as single-device tests).
- [ ] Setup: put B in A's household without the invite UI. The invite sheet sends its link through the share sheet, which Maestro can't read, so a setup script does it against local Supabase: `.maestro/scripts/join-household.js` (a Maestro `runScript`, using its `http` and `json`) signs in as A and as B with the dev email + code stub (Mailpit, as `sign-in-code.js`), finds A's personal household, creates an invite as A (`create_household_invite` or whatever the invite RPC is called; read `supabase/migrations/`) and accepts it as B through the same RPC the join screen calls. Use only the anon key and the users' own sessions, not the service role, so it goes through RLS like the app. The step runs after both users have signed in on their devices (so each has its personal household) and before either opens the shared list. Testing the invite UI itself is a separate test, later.
- [ ] Test: a check-off reaches the other phone. `.maestro/two-devices/check-off/`: A signs in on device A; B signs in on device B; the setup step joins B to A's household; B switches to A's household's Groceries list (through the Your lists sheet) and waits for it to load; A adds Bananas; B sees "Check off Bananas" within 5 s; A checks Bananas off; B sees Bananas leave the unchecked items and the "Checked · 1" header appear within 5 s; B adds Milk; A sees "Check off Milk" within 5 s. Each step's file starts with a comment saying what it checks.
