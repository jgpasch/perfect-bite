# Admin portal

<!-- Status: ready. Spec: 4.12, 5. -->

Goal: a small web app, run locally against hosted Supabase, for the jobs the dashboard makes awkward: find a user and change their plan, edit what each plan includes and its monthly limits, and see how much of each AI feature people use. It lives in `admin/` in this repo. The dashboard and the `admin.*` SQL snippets stay for everything else (deleting a user, reading logs).

**Depends on the Plans section of `tasks.md`** (none / basic / plus / unlimited, no global caps, `plan_limits` and `private.monthly_limit`, usage rows kept 40 days, `private.recipe_photo_ai_usage`). Move these tasks into `tasks.md` after it, in order, once it's done; they use its names and tables.

## Decisions

- **Who is an admin**: a `private.admins (user_id)` table and `public.is_admin()`, not a role in the JWT, so removing an admin takes effect at once. Admins are added and removed in the Table Editor.
- **The server checks every action.** The portal holds only the project URL and publishable key and signs in like the app does. Every admin action is a `public.admin_*` SQL function (`security definer`) whose first step is `private.require_admin()`, which raises `not authorized` (`42501`) for anyone else; execute is granted to `authenticated` only. The `admin` schema and its revokes don't change: the dashboard snippets keep working, and portal functions write `admin.admin_actions` with `performed_by` set explicitly to `auth.uid()::text` (the column defaults to `session_user`, which is `authenticator` for an API call). Rows from the dashboard keep `postgres`; the portal shows them as "Dashboard". The login screen is only UX.
- **Sign-in is Google**, the same provider as the app, through Supabase's OAuth redirect. Not email codes: turning on email sign-in on hosted would let anyone create an account by email. Against local Supabase the portal also offers the email code (the code arrives in the local mail viewer, as for the app's dev stub).
- **Usage comes from the existing per-user usage tables**, which the Plans section keeps for 40 days and counts on every plan. So the portal shows this month and a 40-day daily series; there's no longer history. Counts only: no prompts, links or names. `ai_calls` still has no user id (6.5).
- **Plans are edited as data.** The six feature keys are fixed in code (each is enforced by an Edge Function); the portal combines them into plans and sets their limits. A plan that has `recipe_import` or `recipe_import_photo` must have `categorize`, enforced by a trigger so Table Editor edits obey it too.
- **`admin/` is its own Yarn project** (own `package.json` and `yarn.lock`), not a workspace, so Next.js's React can't clash with Expo's in a hoisted `node_modules`. The root's TypeScript, ESLint, Jest and Metro ignore it.

## Look: "Pantry, back office"

Recognisably the app, made for a laptop. Same as the app: Bricolage Grotesque titles (800, −0.025 em) over Figtree, soft white cards on the pale green ground, round initial avatars, light and dark following the system, and DESIGN.md's colours as CSS variables (no hex in components). Different: a deep-green sidebar (the app's `primary`, darkened) with white text and a small "Back office" pill beside "The Perfect Bite"; dense tables with hairline rows and tabular figures; and each AI feature keeps one aisle colour everywhere (usage tiles, charts, plan grid), so it reads at a glance. No floating tab bar, no phone frames.
