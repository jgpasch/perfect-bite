The app's screens stay in English for users until the **Switch on Spanish** section: until then the app's supported languages are English only, and the Spanish UI shows only in a development build (`EXPO_PUBLIC_FORCE_LANGUAGE=es`) or through Settings > Language. **Spanish input** is different: typing Spanish, and the same thing in either language being one item, works whatever the app's language, so it reaches users as soon as it lands.

Units are a US supermarket's whatever the language (spec 4.15); a metric choice is planned separately in `future/units-tasks.md`.

Before any task that touches `expo-localization` or app config, read the SDK 57 docs: https://docs.expo.dev/versions/v57.0.0/sdk/localization/ and https://docs.expo.dev/guides/localization/ (the plugin's `supportedLocales`, and the `locales` key with `ios.infoPlist.CFBundleAllowMixedLocalizations` for translated permission strings).

## Spanish input

Goal: typing in Spanish works as well as typing in English (amounts and units parse, plurals and accents match), and the same thing typed in either language is one item for a household: `pepino` and `cucumber` share an aisle, tint each other and Combine (spec 4.15's linked ingredients).

- [ ] Fold accents in the ingredient key (spec 4.15). `normalizeIngredientName` (`src/shared/ingredient-normalizer.ts`, shared with the Edge Functions) strips diacritics after its NFC step (`limón` → `limon`, `jalapeño` → `jalapeno`, `crème fraîche` → `creme fraiche`); display names keep what was typed. A migration merges every existing key that changes into its folded key across every table that holds an ingredient key (the catalog: keep the categorized row, prefer `seed`; `ingredient_usage` and `ingredient_unit_usage`: sum counts, max `last_used_at`; household overrides: keep the newest; list items, contributions, recipe ingredients: rewrite the key), and the app runs the same merge on its local SQLite once (a backfill marker, like the other one-time backfills). Drop the seed's now-duplicate accented spellings (`jalapeños`, `gruyère`, `tajín`, `sazón`, `rosé`, `café bustelo`...) and regenerate the seed SQL. pgTAP and Jest tests for the merge, including two rows that fold to one in the same household. The user pushes the migration to hosted Supabase (hand them the command).
- [ ] Spanish amounts in the quantity parser (`src/shared/quantity-parser.ts`, spec 4.15): Spanish number words (`un`/`una`/`uno` to `veinte`, `medio`/`media` = 0.5, `media docena`), Spanish unit spellings mapped to the existing units (no new units; `pieza(s)`/`pza(s)` is a plain count), and a `de` right after a unit dropped from the name. `half and half`-style guards: a name that merely starts with a number word and no unit stays a name. Accepted whatever the app's language. Table tests, including `2 tazas de harina`, `1 kilo de jitomate`, `medio kilo de queso oaxaca`, `media docena de huevos`, `3 piezas de aguacate`, `1 manojo de cilantro`, `2 dientes de ajo`, `una lata de chiles chipotles`, and that every English case still passes. - [ ] Categorizer translates and links (`categorize.v3`, spec 6.4, 4.15). Names may be English or Spanish (Mexico), shelved and given units as a US supermarket would whatever the language. Each answer gains `lang` (`'en' | 'es' | 'other'`), `translation` (Mexican Spanish for an English name, English for a Spanish one; null when there's none or it's the same word, like `chocolate`) and `exact_equivalent` (true only when the two are the same thing on a shopping list). The prompt uses the shared word list and no-link examples from the seed task; raise `maxOutputTokens` per name for the extra fields. The server normalizes the translation with the shared normalizer and drops it if empty, over 64 characters, not just letters, spaces, hyphens and apostrophes, or the same key as the name. Otherwise it upserts the twin row (its `lang`, the name's category, unit and `is_grocery_item`, `categorized_by` the model, `household_count` 0 so spec 6.5 keeps it out of other households' autocomplete) and, when `exact_equivalent`, links the pair at once: the non-English row's `same_as` is the English row, `linked_by` the model id. A twin that already exists keeps its own category and unit and is only linked; if either side already has a link, nothing changes (a seed link always wins). The response and the device catalog pull carry the new rows and links. Add `yarn ai:unlink` (`--by <linked_by>` or `--name <key>`, a dry run unless `--apply`) to clear links in bulk; the user runs it against hosted. Golden set: about 40 Spanish names (`jitomate`, `tomate verde`, `chile serrano`, `epazote`, `queso oaxaca`, `crema`, `tortillas de maíz`, `bolillo`, `jamaica`, `Fabuloso`, two injection names in Spanish) and translations for the English ones already there, each with its expected translation and `exact_equivalent`, including the no-link cases; the eval scores links, counting a wrong link worse than a missing one. Deno tests with the mock model (twin created, linked, already-existing twin, already-linked side, rejected translations, injection).
