## Push notifications

Goal: household members hear about each other's list activity when the app is closed: "Alex added milk, eggs and 4 more to Groceries" and "Alex is shopping at Groceries". This is spec 11.1 coming out of Later, and the in-app banners (4.11) are the base it builds on. iOS only (Android isn't a target, but nothing here should rule it out: keep the Android channel call and the `platform` column). Delivery is Expo Push (`expo-notifications`, which talks to APNs for us). Spec 11.1 says to queue from a trigger on `list_items` inserts, but a Combine adds a **contribution** to an existing open item and inserts no `list_items` row. So "added" events come from `list_item_contributions` inserts, and "shopping" events from `list_items.checked_at` going from null to set. A trigger queues each event on a pgmq queue `household_events`, as stash does for captures. A worker Edge Function `send-notifications`, run by pg_cron every minute, groups the events and sends one push per group to the household's other members. The person who made the change never gets a push about it.

**Grouping.** A group is (household, actor, list, kind). It sends once it has been quiet for 60 s (its newest event is at least 60 s old) or its oldest event is 5 minutes old, whichever comes first, so a burst of adds becomes one push. At send time the worker re-reads the rows, so an add that was undone (the contribution is soft-deleted) or an item unchecked again doesn't count, and a group left with nothing is dropped without sending. **Added**: counts the live contributions. The body names up to two items by `display_name`, then "and N more". A group that is all one recipe's add reads "Alex added Tacos (8 items) to Groceries". **Shopping**: sent at most once per (actor, list) in a 2-hour window, on the first checks after none for 2 hours, never once per check. **Stale events**: a device that was offline in the store syncs its checks hours later. Drop events whose row time (the contribution's `created_at`, the item's `checked_at`) is more than 15 minutes older than the worker's clock, so nobody hears "Alex is shopping" after Alex got home. **Actor name**: the first word of `profiles.display_name`.

**Recipients.** A recipient is any current member of the household, other than the actor, who has at least one push token, has that kind turned on, and isn't in their quiet hours, judged in their own time zone. Membership is read when the push is sent, so someone who left the household gets nothing. Tapping a push opens that list (`/list/<id>`).

- [ ] Server: push tokens and notification settings. New migration in `supabase/migrations/`. **`public.push_tokens`**: `token text primary key` (the Expo push token, `ExponentPushToken[…]`), `user_id uuid not null references auth.users on delete cascade`, `platform text not null check (platform in ('ios', 'android'))`, `created_at` and `updated_at timestamptz not null default now()`, with an index on `user_id`. Turn RLS on, with no direct table access for `authenticated`. Writes go through two `security definer` functions granted to `authenticated` only. `public.register_push_token(p_token text, p_platform text)` validates the token's shape (`raises invalid token`) and upserts it for `auth.uid()`; a token already held by another user moves to the caller, because the device changed hands on sign-in. `public.unregister_push_token(p_token text)` deletes the caller's row and is a no-op if it isn't theirs. **`public.notification_settings`**: `user_id uuid primary key references auth.users on delete cascade`, `items_added boolean not null default true`, `shopping boolean not null default true`, `quiet_hours_start time` and `quiet_hours_end time` (both null = off; a start later than the end wraps past midnight), `time_zone text not null default 'UTC'` (an IANA name, checked against `pg_timezone_names` in a trigger or in the setter), and `updated_at`. It has RLS: select, insert and update for the user's own row only. A missing row means the defaults. The table is per user, is read and written online, and doesn't go through the outbox or sync (the settings screen needs a connection to change it, like Leave household does). Add a `private.push_recipients(p_household_id uuid, p_actor uuid, p_kind text, p_at timestamptz)` function for the worker: members of the household minus the actor, with their tokens, filtered by the kind's setting and by quiet hours in each user's `time_zone`; execute for `service_role` only. pgTAP tests in `supabase/tests/`: register, re-register (moves the token, bumps `updated_at`), unregister someone else's token (no-op), a bad token shape, RLS on both tables (a user can't read another's settings or any token), the defaults when there is no row, and `push_recipients` (the actor is excluded, a former member is excluded, a kind switched off, quiet hours inside, outside and wrapping midnight across time zones, a user with no token). Check that `admin.delete_user` (and its tests) still pass with the new FKs.

- [ ] Edge Function: `send-notifications` worker. New function `supabase/functions/send-notifications/` in the same shape as `import-recipe`: `index.ts` (wiring), `handler.ts` (pure logic), `store.ts` (database), `expo.ts` (Expo Push client) and Deno tests. It is called only by pg_cron with the service-role key; use `withSupabase` with service auth, or check the bearer against a secret, and answer 401 to anyone else. **Each run**: read up to 500 messages from `household_events` with `pgmq.read`, using a visibility timeout of 2 minutes (exposed through a `private` RPC for `service_role`, since pgmq isn't in the exposed schemas). Group them per the goal's rules, using the events' `at` and the worker's clock. Leave the messages of groups that aren't ready yet to reappear, and archive (`pgmq.archive`) every message that was sent, dropped as stale or dropped as empty. For a ready group, re-read its rows to count what's still live, build the title and body, resolve recipients with `private.push_recipients`, and send. Keep the shopping 2-hour window in a small `private.push_sent (household_id, actor, list_id, kind, sent_at)` table, which also serves as a log; add a daily pg_cron cleanup of rows older than 7 days. **Messages**: title = the list's name; body = "Alex added milk, eggs and 4 more", "Alex added Tacos (8 items)" or "Alex is shopping"; `data: { url: '/list/<id>', kind, householdId }`; `sound: 'default'`; on iOS a `threadId` per list, so a list's pushes stack in Notification Center. Names come from the rows and are text only, so check that an item name with markdown or emoji goes through as-is. **Expo client**: POST to `https://exp.host/--/api/v2/push/send` in chunks of 100, with `Authorization: Bearer $EXPO_ACCESS_TOKEN` when that secret is set (add it to `supabase/functions/.env.example`, commented, unset meaning no header). Retry 429 and 5xx with backoff, up to 3 tries within the run. On a ticket error `DeviceNotRegistered`, delete that token. Store the `ok` ticket ids with their tokens in `private.push_receipts (ticket_id, token, created_at)`. **Receipts**: each run, also check receipts at least 15 minutes old through `/--/api/v2/push/getReceipts`; delete tokens whose receipt says `DeviceNotRegistered`, delete checked receipts, and drop any older than 24 hours. **Schedule**: a migration that adds `pg_net`, and a `cron.schedule('send-notifications', '* * * * *', …)` that calls `net.http_post` to the function.
